# v0.8.1 —— 闹钟在 AOSP 时钟上被拒

v0.8.0 之后的补丁版：把「设置闹钟」「新建日程」在**非厂商时钟 / 日历**上跑了一遍，
两个都真出了问题。功能没变，只修毛病。

## 修了什么

### 设置闹钟在某些设备上直接失败

在 AOSP / Pixel 的时钟（DeskClock）上，`set_alarm` 会被系统以 `SecurityException` 拒绝：

```
Permission Denial: starting Intent { act=android.intent.action.SET_ALARM
  cmp=com.google.android.deskclock/...HandleSetApiCalls }
  requires com.android.alarm.permission.SET_ALARM
```

DeskClock 把处理这个 action 的界面声明成需要 `com.android.alarm.permission.SET_ALARM`。
这条权限是**普通级**（装包即授、不弹框），补进清单即可 —— v0.8.0 那句「不需要任何权限」
对厂商时钟成立，对 AOSP 时钟不成立，而后果是**静默失效**：报错在 logcat 里，
用户只看到「闹钟没设上」。

### 新建日程会触发一次权限拒绝

`add_calendar_event` 每次都会在 logcat 里留一条
`Permission Denial: opening provider ...CalendarProvider2`。原因是我们只给了 intent 的
`data` 没给 MIME，系统解析时就会拿**应用进程的身份**去问日历 provider 要类型 ——
而应用没有 `READ_CALENDAR`（也不该有）。给 intent 显式带上
`vnd.android.cursor.dir/event` 之后不再查。

功能没受影响（intent 仍能落到日历 App），修的是每次调用都留一条看起来像越权的日志。

## 验证

| 项 | 结果 |
|---|---|
| 门禁三条 + 单测 | ✅ |
| **闹钟**：`set_alarm` → 时钟 App 预填 | ✅ 模拟器（API 36 / x86_64）实测预填 `7:00 AM` + 备注 |
| **日程**：`add_calendar_event` → 日历 App 预填 | ✅ 模拟器实测预填标题 / 起止时间 / 地点，且不再有权限拒绝 |
| **闹钟与日程：真机** | ❌ **未验**（模拟器覆盖了 AOSP 那条路；厂商时钟那条路只有 v0.8.0 之前的印象） |

模拟器上没有 Google 账号，Google 日历进不去编辑界面，所以日程那条另装了 Etar
（本地离线日历）来读预填内容。闹钟走的是 AOSP DeskClock —— 正是出问题的那一支。

## 安装

```bash
adb install -r tappet-v0.8.1-arm64-v8a.apk
sha256sum -c tappet-v0.8.1-arm64-v8a.apk.sha256   # 可选
```

从 v0.8.0 覆盖安装即可，数据不受影响。
